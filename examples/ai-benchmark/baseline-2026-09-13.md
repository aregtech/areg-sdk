# Baseline, 2026-09-13: one task, areg and gRPC, side by side

One cold agent run per framework, same task, same agent, same model, same effort, same
fix bound, same machine, same revision of this repository. It is the first pair in which
the gRPC run provably had no areg documentation or source available, and it is the
baseline later runs are compared with.

**The question it answers.** gRPC stands for what the model already knows: it was
trained on it and needs no documentation from us. areg stands for what the model has
never seen: everything it knows about areg in this run comes from `AGENTS.md`,
`docs/agent/` and the generators in `tools/agent/`, read during the run. Does that
"learning on the fly" deliver the same result, and what does it cost?

The sanitizer finding is `runtime error: member call on address ... which does not point
to an object of type 'CoffeeServiceProvider'`, in the provider's constructor: `self()` is
called while a base class is still being initialized, which the C++ standard leaves
undefined. The line is the one areg's generator writes and its documentation teaches; the
agent did not invent it. **The two rows are not equally strict:** areg is compiled from
source inside the run, so the sanitizers check its framework code too, while gRPC links
prebuilt system libraries the sanitizers do not see.

## 3. What this pair shows

**On the checklist, quality is a tie; under the hidden probes, gRPC is ahead by one
requirement.** Both implementations pass every scenario the agents wrote, ten times in a
row, with a late-starting server and with the server killed at three points. But the areg
client, started with no server at all, waits forever, and after a loss it takes 18-20 s
to give up where the gRPC client takes 0.1 s. The cause is in areg's own guidance, not in
the model: the documentation tells a client that a lost connection comes back by itself,
and the generated client's only deadline starts after the first connection.

**The documentation answered every question the areg run had.** Zero filesystem
searches, zero framework sources opened, ten pages opened, each one a page the guide
routed it to. The gRPC run, with its own training and no documentation, made four
filesystem searches to find out how protobuf is installed.

**Learning on the fly is paid for in reasoning, up front.** The areg run thought more:
53K reasoning tokens against 39K, three quarters of its output. Two thoughts carry most of
it, the design (12.5K) and the implementation (19K). After that it built once, fixed once,
ran once, fixed once.

**Recalling from training is paid for in iterations.** The gRPC run thought less and
tried more: 77 requests against 25, 9 build-and-fix and 10 run-and-fix cycles against 1
and 1. Its own report names a self-deadlock in its event path, stale events bleeding
between steps, and connection loss reported as a refusal: the class of defect a framework
removes from what has to be written. It wrote 2.8 times as much C++ by hand.

**Per request, areg is expensive and gRPC is cheap; per task it is the other way round in
this pair.** An areg request carries a larger context ($0.078 against $0.034), and there
are a third as many of them.

## 4. How far these numbers can be trusted

**Setup: objective.** Same revision, same clean tree, same agent version, model, effort,
bound, tools and machine, started 24 minutes apart. The areg arm verifiably built against
the copy it read, not an installed package, and the copy was unchanged at the end
(fingerprints of 60 files). The gRPC arm had exactly one file of this repository beside
it, the scenario runner, and the run refuses to start otherwise.

**Cold start of the gRPC arm: proven for files, not for the name.** Every tool call of the
gRPC run was checked: none opened, listed or searched anything of areg, and the only file
of this repository it touched was the scenario runner. But the agent was *told* that areg
exists: the name is in the task's preamble and in the runner's `--help` line, and its
prompt called the runner's directory "another framework's checkout". None of that carries
information about areg beyond the name. It has
been removed since, and the script now refuses to start a gRPC run whose task or prompt
names areg.

**Quality row: the checklist is at the ceiling; the hidden probes are not.** Both agents
report 15 of 15, including two items -- *no wait longer than 20 seconds* and *no
busy-waiting* -- that neither run's own output shows. The hidden probes test those items
directly, the same way for both arms, and that is where the arms separate: 4 of 5 against
5 of 5.

**Cost, requests and cycles: one draw per arm.** The same revision run again gives a
different number. Measured spread of the same tree in earlier runs of this benchmark:

| arm | draws on identical agent input | range |
|---|---|---|
| areg | this revision's input, 2 draws: $1.941, $2.050 | 6% |
| areg | earlier revisions, 5 draws on one revision | 45% |
| gRPC | provably cold: this run only, $2.631 | -- |
| gRPC | earlier runs, not provably cold, 6 draws | $1.30 .. $3.19, median $2.18 |

The areg figure is supported by a second draw on identical input. The gRPC figure is a
single draw, above the median of its earlier (not certified) runs. **The 1.36x cost ratio
is therefore not a result to state on its own.** What holds across the runs of
2026-09-12 and 2026-09-13 -- 11 areg, 3 gRPC, several revisions -- is the *shape*:

| | areg, 11 runs | gRPC, 3 runs |
|---|---|---|
| API requests | 24 .. 52, median 34 | 42 .. 77, median 57 |
| reasoning tokens | 34.6K .. 65.9K, median 53.3K | 29.3K .. 47.3K, median 39.3K |
| filesystem searches | 0 in every run | 1, 2 and 4 |

## 5. Not comparable, and why

**Wall time.** 30 of the gRPC run's 40 minutes were two `find /` commands that each ran
into the agent's 600-second command limit on a mounted Windows drive. That is the
machine, not gRPC. In the other direction, the areg run compiles the whole framework from
source during its first build, while gRPC links prebuilt system packages. Use model time
(API) instead: 12.3 against 14.5 minutes.

**Cost per request.** It is lower on gRPC because each request carries less context, not
because the work is cheaper; the total is what the task costs.

## 6. For a slide

Safe to state from this pair:

- **Same checklist score**: both 15 of 15, every scenario passing ten times on an
  independent re-run.
- **Hidden probes find what the checklist cannot**: gRPC 5 of 5, areg 4 of 5 -- the areg
  client has no deadline for a server that never comes. A benchmark that can fail the
  framework it was built to promote is the one worth trusting.
- **The documentation replaced the training**: 0 filesystem searches, 0 framework
  sources read, 10 routed pages -- against 4 searches for the framework the model was
  trained on.
- **Think first, or try often**: areg 25 requests, 1 build fix, 1 run fix, 53K reasoning
  tokens; gRPC 77 requests, 9 build fixes, 10 run fixes, 39K reasoning tokens.
- **Less code by hand**: 449 lines of C++ against 1,257.
- Agent Claude Code 2.1.270, model Claude Sonnet 5, effort medium, fix bound 15.

State only with "one run each": the cost, $1.94 against $2.63.

Do not state: wall time; a cost ratio without its spread; "areg is better quality" --
this task cannot show it.
