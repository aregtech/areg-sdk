=== THE AREG WRAPPER WITHOUT THE AGENT LAYER ===============================

run-benchmark.sh --layer off builds the prompt from this file. The snapshot it
hands the agent is the framework as a plain checkout gives it: the sources, the
human documentation, the examples and the code generator. Nothing written for a
coding agent is in it, and the prompt below names none of it.

  areg-sdk  the snapshot, read only
  runner    the framework-neutral scenario runner, staged inside the snapshot
  task      the task file, staged inside the snapshot
  project   a C identifier. The directory name and the CMake project name.

--- PROMPT BEGINS BELOW THIS LINE ----------------------------------------

You are building an application on top of areg. These are the settings for this task:

  areg-sdk  <areg-sdk>
  task      <task>
  project   <project>

"areg-sdk" is the framework checkout, readable in this session: its sources, its
documentation, its examples and its code generator. It is read only: never write into
it, never modify it, never cd into it. Build the framework from this checkout as part
of your project's build; never download areg, never install it.

**The directory this session started in is the project root.** Work there, exactly
there. Do not create a directory for the project and do not change to another
directory.

The process runner the report is scored with is

  <runner>

It is framework-neutral. Read its --help once, and write the scenarios.json it
describes. Nothing else beside it is yours to open, and you never write into its
directory.

Do this:

1. Read <task>. It is the whole specification: what the programs must do, how to
   prove it, and the acceptance checklist you are scored on. It names no framework on
   purpose.

2. Carry it out end to end -- contract, code, build, run, fix, report. You are not
   finished when the code is written. You are finished when it builds and every
   scenario exits 0, or when the task file's stop rule tells you to stop and report
   instead.

3. End with the report the task file asks for -- the small table and no more. Do not
   measure anything to fill it in and do not guess a number.

Rules for this task, above anything else:

- It is a project of its own. Do not add it to any other project's build files,
  and write no IDE or editor project files.
- **One class, one .hpp and one .cpp, named after the class.** Never put two
  components in one file and never define a class inside a main().
- **Never edit a generated file.** Change the interface document instead.
- **You may read anything in areg-sdk, examples included. No file arrives by copy:**
  every file in the project is written by you or generated by a tool.
- Never commit anything, and never run a git command.
- Do not write a ReadMe.
- **Never start the processes by hand.** No program launched in the background, no
  sleep command and no process killed from the command line. A scenario is what you
  run; the runner's --verbose prints every line each process wrote and --only <name>
  runs one scenario. They leave nothing running.
- **Every `-j` carries the number 8**: `cmake --build build -j8`.

Two habits that halve the cost of the same work. Every request re-sends the whole
conversation, so the bill is the number of requests multiplied by how much each one
carries. Both are free to follow and neither changes what gets built.

- **Put independent calls in one request.** Reading eight pages is one request, not
  eight. A header and its source are written together. Only split where the next
  thing genuinely depends on the result of the last -- a build, a check, a scenario run.
- **Never pour a log into the conversation.** It stays there for every later request.
  Everything that can print hundreds -- a file search, a recursive listing, a raw
  compiler run -- is filtered or cut to its first lines before you ask for it.

Fix -- bounded, then stop. You are finished when it builds **and** every scenario
exits 0. Keep going until it does, within at most **3 build-and-fix cycles** and at
most **3 run-and-fix cycles**. Fix the cause, not the symptom: widening a timeout,
adding a sleep, retrying, deleting an assertion or loosening what a scenario expects is
not a fix. Still failing after the third cycle of either kind? **Stop and report**:
what fails, the exact output, what you tried, what you think the cause is.

**Every acceptance item in the task file not marked (code) is an `expect` entry in
`scenarios.json`**, matched against a line the run actually prints -- including the
two that look like they need a terminal. A console quit path is `"stdin": ["-q"]` on
the lead of a scenario of its own; the other side going away is a scenario-level
`"stop"`. An item with no expectation behind it is reported as not passing, however
sure you are of the code.

The report is the one small table the task file asks for, and the only report to
write. Fill it from what you already know and measure nothing to fill it in. The
acceptance count comes from the scenario output, not from a second run.
